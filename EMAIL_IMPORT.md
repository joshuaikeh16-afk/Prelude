# Gmail import and national holidays

Settings now uses compact grouped rows. Account editing, notifications, region, Gmail management and recent memories expand in place. Country, timezone and notification changes save immediately with rollback/error feedback. Profile editing retains one Save action. The event-creation preference is no longer exposed; existing stored choices are preserved. Google Calendar is not presented as a working integration.

Gmail is connected once with read-only Google consent, either during optional Google sign-in or from its Settings row. New connections default to automatic import; existing opt-outs remain respected under secondary Import preferences. Clear one-off calendar invitations with an explicit timezone (or all-day date) import automatically. Plain messages auto-import only if a single explicit full date/time is labelled, a venue and valid explicit timezone are present, and deterministic confirmation language appears without tentative/quoted correspondence. Other supported explicit dates become editable suggestions. Recent imports link to the resulting event. The Supabase storage adapter persists Prelude session credentials but removes Google provider tokens; the optional sign-in grant is handed to the backend from transient callback memory and then cleared. Automatic imports enqueue a unique notification in the existing reminder pipeline; delivery respects browser permission, the account notification preference and VAPID setup.
## Enable the integration

1. Apply `supabase/migrations/20261005_email_import.sql`, then the additive `supabase/migrations/20261006_mail_background_scanning.sql`, after the existing coherent-v1 migration. Credentials and source suggestions are backend-only tables; users import through an ownership-checked RPC.
2. In Google Cloud, enable Gmail API and create a **Web application** OAuth client. Configure the consent screen for `https://www.googleapis.com/auth/gmail.readonly`. For combined sign-in and Gmail consent, configure `GMAIL_CLIENT_ID` and `GMAIL_CLIENT_SECRET` with the **same Google OAuth client** used by the Supabase Google provider, so server-side token refresh succeeds. That client must allow both the Supabase Auth callback URL and the separate `/api/mail/callback` URL for Settings permissions. Add the Gmail read-only scope to that Google application’s consent configuration. During testing, add your test accounts. Public use of this restricted scope requires Google's verification and applicable security assessment: https://developers.google.com/workspace/gmail/api/auth/scopes
3. Add the **exact** callback URL to that OAuth client and set `GMAIL_CLIENT_ID`, `GMAIL_CLIENT_SECRET`, `GMAIL_REDIRECT_URI`, and `MAIL_TOKEN_ENCRYPTION_KEY` on the backend. Generate the key with `node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"`. Keep the key stable: changing it requires reconnecting existing accounts. Never expose these variables to frontend code.
4. Set `PRELUDE_FRONTEND_ORIGINS` to the exact frontend origins, and point the HTML `PreludeConfig.apiBase` at this backend. Development CORS permits Live Server at port 5500 and the local servers on 8080/8081. Production requires explicit allowed origins. For local tests use `http://localhost:8081` and `http://localhost:3000`; use the same hostname, rather than mixing localhost with 127.0.0.1.
5. Serve frontend and backend on the **same site** in production (for example `app.example.com` and `api.example.com`, both HTTPS), or proxy `/api` through the frontend origin. The consent flow uses an HttpOnly SameSite=Lax cookie to bind Google consent to the initiating browser. Cross-site frontend/backend deployments can block that cookie and cannot safely complete this implementation's consent flow.
6. Configure `CRON_SECRET`. `vercel.json` adds `/api/mail/dispatch` every 15 minutes; the job scans up to three due mailboxes per invocation, with a 15-minute minimum between attempts per mailbox. Use a hosting plan supporting this schedule or an authenticated external scheduler. With three mailboxes per 15-minute invocation, latency increases beyond three connected mailboxes. Monitor aggregate failures and scan age; use a more frequent authenticated scheduler or a durable job queue for higher volumes. A 15-minute polling schedule is not instant Gmail push delivery.
7. Connect Gmail. The next server dispatch starts scanning without visiting Settings. **Check now** is a secondary fallback, not a normal prerequisite.

Each scan reads up to 20 matching emails from the last 30 days, using Gmail's query for calendar files, invitations, meetings, appointments, reservations, bookings and events. Pagination uses a frozen query window. A watermark advances only after the window completes; a two-minute boundary overlap and backend-only processed-message ID ledger prevent repeated body reads. A three-minute database lease serializes scheduled/manual scans, with a 45-second scan budget. Partial failures preserve the window/cursor and successful IDs for safe retry. Processed IDs expire after 60 days. Credentials, connection settings and event data are preserved by the additive migration. Message bodies are processed in memory, not retained. Only extracted event fields and the source subject/sender are stored. Attachments are limited to calendar files; remote email images and links are never fetched. Email text is data, never executable instructions.

Duplicate invitations are identified by calendar UID per mailbox. Imports are atomic and repeated requests return the existing event. Matching title/date/time/timezone across mailboxes reuses the existing Prelude event. Disconnecting removes credentials and suggestions and attempts Google token revocation; events already created remain.

This first version skips recurring series and cancelled invitations. It does not automatically reschedule or cancel an already imported event: Prelude fixes an event's identity after creation. Free-form messages without an explicit full date are not guessed. Plain emails without an explicit valid timezone or strong labelled confirmation remain suggestions. Supported dates include English month names/abbreviations, ordinals with optional “of”, and ISO dates; supported times include AM/PM and 24-hour HH:mm. Ambiguous numeric dates and vague relative dates are not guessed.

## Scheduling locally and in production

**Local development does not run Vercel cron.** After applying both mail migrations and configuring `CRON_SECRET`, run the backend normally, then run `npm run mail:worker` in another backend terminal. This independent Node process calls the protected dispatch endpoint immediately and every 15 minutes, even with the browser closed. Stop with Ctrl+C. It must remain running; it is a development adapter, not a durable hosted scheduler. `npm run mail:dispatch` invokes one dispatch for diagnostics. Neither command prints mailbox content or credentials. `MAIL_DISPATCH_URL` optionally selects a trusted HTTPS backend endpoint; HTTP is allowed only on loopback.

For deployment, deploy the backend `vercel.json` with a Vercel plan supporting its 15-minute Gmail and one-minute notification cron expressions, and set `CRON_SECRET` in the production environment. Vercel supplies `Authorization: Bearer <CRON_SECRET>`. Alternatively configure an external scheduler to call GET or POST `/api/mail/dispatch` every 15 minutes with that header, and schedule the existing `/api/notifications/dispatch` separately for import notices/reminders. Missing or incorrect secrets get HTTP 401. Do not place secrets in query strings. Verify scheduled invocation logs/aggregate counters and mailbox scan timestamps after deployment. No scheduler has been deployed by this refactor; background scanning is inactive locally until the worker runs, and inactive in production until the scheduled jobs are configured.

## National holidays

`/api/holidays` tries Calendarific's national feed, then Nager.Date's globally applicable public holidays. Nigeria has a local fallback for recurring fixed and Gregorian Easter dates when both feeds are unavailable. The 2026 fallback also includes officially announced Eid-ul-Fitr (March 19–20), Eid-ul-Adha (May 27–28), and Eid-ul-Mawlid (August 25). Those dates are year-specific and are never extrapolated. This fallback is explicitly partial; further special declarations and substitute days require the live feed. Sources: https://interior.gov.ng/federal-government-declares-thursday-19th-and-friday-20th-march-2026-as-public-holidays-to-mark-eid-ul-fitr/ , https://fmino.gov.ng/federal-government-declares-wednesday-27th-may-and-thursday-28th-may-2026-as-public-holidays-to-mark-eid-ul-adha-celebration/ , and https://interior.gov.ng/news-media/press-release/ . Set `CALENDARIFIC_API_KEY` for the full live Nigerian feed. Provider failures no longer prevent recurring Nigerian holidays from appearing.

The calendar outlines holiday dates, includes holiday names in accessible date labels, lists national holidays for the displayed month, and explains partial coverage. Country remains configurable in Settings.

References for the recurring Nigerian dates include the Ministry of Interior's Easter/Workers' Day declarations at https://interior.gov.ng/1519-2/ and Democracy Day declaration at https://fmino.gov.ng/federal-government-declares-june-12-2026-public-holiday-in-commemoration-of-democracy-day/ . Calendarific national filtering: https://calendarific.com/api-documentation .

## Validation

Run `npm test`, `npm run test:database`, and `npm run test:browser` in `prelude-html`, and `npx tsc --noEmit` in `backend`. Unit tests cover confidence criteria, date variations, lease/busy behavior, incremental checkpoints, processed-message skipping, partial failure recovery, auto-import/review separation, scheduler authentication, token refresh and date/timezone conversion, uncertain/cancelled/recurring invitations, encrypted-token integrity, redirect validation and holiday-provider fallback. Database tests cover scan-lease exclusivity/expiry, ledger isolation/cascading removal, unique import notices, additive migration replay, credential isolation, cross-user imports, idempotence, automatic-import restrictions and draft preservation. Browser tests use mocked provider responses; a real Gmail consent/refresh/revocation test still requires your configured Google OAuth application and a test mailbox.

## Gmail button disabled

Run `npm run check:gmail` from `backend`. This validates credential presence and performs actual zero-row GET queries against the required tables and columns without retrieving mailbox data. A `PGRST205` result means the email migration has not been applied to this Supabase project (or its schema cache has not refreshed).

In the same Supabase project used by Prelude, open **SQL Editor → New query**, paste the complete contents of `supabase/migrations/20261005_email_import.sql`, and run it, then run `supabase/migrations/20261006_mail_background_scanning.sql`. Apply the coherent-v1 migration first if its dependencies are missing. Then rerun `npm run check:gmail` and refresh Settings. The migration creates protected email tables and the atomic import function; it does not delete existing events or drafts.
